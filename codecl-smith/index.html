CodeCL-smith

A toolkit that converts (code benchmark + verifier) into ordered continual-learning streams — to benchmark how well a model learns from verifiable feedback at test time. 2026-07 · design page, intentionally plain.

source tasks + verifier ──► compose ──► sequence manifest (the benchmark instance)
                                              │
                              run ◄──────────┘   prequential loop: solve → verify → feedback → update
                               │
                              score ──► learning curves, ΔAUC vs frozen, probes, slices

1 · The base case

Take 10 tasks, batch size 2. The learner starts with state s₀ (empty playbook / frozen weights). For each batch t:

solve all of batch t using state s_{t-1}     ← every task is scored HERE, exactly once
verify each solution  → VerifierReport(s)
aggregate + render    → feedback text (at the configured ladder rung)
learner.update(...)   → state s_t

This is prequential (test-then-learn) evaluation: no task's score is ever contaminated by its own feedback — only by what came before it. The frozen model runs the same stream as the control arm; the difference is the value of learning.

Why streams at all? Static benchmarks measure what a model already knows. A stream measures whether it can get better while working — the thing that matters for deployed coding agents. No existing benchmark does this for code with executable feedback (see §6).

2 · What is a benchmark instance?

An instance is a SequenceManifest JSON — fully reproducible, shareable:

fieldmeaning
source + dataset_hashwhich tasks; the hash is re-checked at run time (data changed ⇒ manifest refuses to run)
order_rule + seedhow the K sequences were generated
sequences[]K orderings of the same task set, each a list of batches (task ids)
probes[]where retention / unseen-twin probes are inserted

The same 100 tasks yield many different streams. Ordering rules:

balanced latin-square-style rotation — every task appears early/mid/late across the K sequences, enabling per-task P(correct | position) regression that controls for task difficulty clustered pattern families adjacent in time (strongest learning signal) interleaved families alternate (tests interference) curriculum by difficulty temporal by real contest date (LiveCodeBench) random control

CL only has signal when patterns recur. Ordering is therefore a first-class experimental variable, not a preprocessing detail — and results are reported across multiple orderings with variance, never from a single sequence.

4 · Scoring

One number hides everything interesting, so a run reports:

prequential accuracymean over all first encounters (± across sequences)
learning-curve AUCarea under accuracy-vs-position — rewards learning fast, not just learning eventually
gainlast 20% − first 20% of the stream
ΔAUC vs frozen + McNemarpaired by (sequence, task); exact binomial test on discordant pairs
probe metricstwin (did the pattern transfer?) and retention (memorized?) — kept apart on purpose: retention-high + twin-low = “memorizing, not learning”
slicesper verifier category and task family — compliance-shaped vs capability-shaped failures behave differently under text feedback
cost sidebartokens, update overhead, state-size curve (guards against unbounded-memory “wins”)

5 · Design choices (and why)

  1. Verifiers are stateless; the Aggregator owns cross-task. One (task, solution) in, one report out. Anything spanning tasks — failure-pattern counts, windows — happens in a single aggregation layer. Keeps every verifier trivially testable.
  2. Measurement and feedback are two projections of one report. The scorer reads passed/score; the learner sees render(report, rung). The ladder is a pure function, so the self-test can assert exactly what each rung leaks (binary must not contain tracebacks, patterns must carry family markers…).
  3. Self-test gate, on by default. Before any run: (a) environment preflight — can each requested source/verifier/backend actually run here? warn the user instead of producing garbage; (b) oracle injection — known-good reference must pass, known-bad must fail with the right category. Motivated by hard experience: four separate “the model can’t do X” findings that were actually harness bugs. The gate caught a real bug (relative path + cwd) on its first-ever run.
  4. Probes after the update, excluded from the headline. A twin probe asks “you just learned from that batch — does it transfer to a fresh instance of the same pattern?” Retention probes are deliberately leak-suspect (that’s what they measure) and never merged into headline accuracy.
  5. Leak audit with severities. Reference (answer) content in learner state = always flagged. Task-id mentions = informational — by-design for replay learners, a smell for compressing ones.
  6. Workspace isolation. Every execution gets its own directory as cwd+TMPDIR; candidate code never runs in a shared directory. Parallelism follows the protocol: solves within a batch share s_{t-1} (parallelizable), updates are serial at boundaries, sequences are fully independent.
  7. Everything is a registry. Sources, verifiers, learners, backends, orderings, ladder rungs — adding one is a file plus a decorator, and it appears in the CLI.
  8. Honest resume. Learner state can’t be replayed from records (yet), so a partial sequence restarts rather than silently resuming with wrong state.

6 · Does it work? (validation so far)

A deterministic mock backend simulates learning (a task family is solved iff the context mentions it), so curve shapes are predictable — and reproduced end-to-end:

armpredictedobserved (built-in EvalPlus-style set)
frozenflatflat at 0.500
context + binaryflat (rung carries no family info)flat at 0.500, Δ=0
context + patternsrises after a family first fails0.667, Δacc +0.167, twin 1.0
playbook + patternsrises via distilled hints0.667, Δacc +0.167, twin 1.0

Real-data smoke (mock solver on real tasks): all 164 HumanEval canonical solutions pass our harness; BFCL v4 synthesized reference calls pass the AST oracle; real Codeforces IO cases produce correct expected/actual evidence. A playbook arm on real HumanEval: Δacc +0.400 vs frozen, McNemar p = 0.0078 (8 learner-only wins, 0 frozen-only).

8 · Try it

codecl compose --source humaneval --limit 10 --n-seqs 2 --batch-size 2 \
    --order clustered --probes retention --out streams/he.json
codecl run  --manifest streams/he.json --learner frozen   --feedback-level none     --out runs/frozen
codecl run  --manifest streams/he.json --learner playbook --feedback-level patterns --out runs/playbook --debug
codecl score --run runs/playbook --vs-frozen runs/frozen
